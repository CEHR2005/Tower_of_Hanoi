# Производительность и проверка

Измерения выполнены 2026-10-08 в Linux/Docker на доступной виртуальной машине.
Это результаты данной реализации, компилятора и нагрузки; не доказательство
абсолютного превосходства алгоритма и не сравнение всех возможных реализаций.

## Методика

- Debian 12, GCC 12.2.0, CMake 3.25, C++20, Release `-O3 -DNDEBUG`.
  Без LTO, `-march=native`, сторонних benchmark-библиотек и многопоточности.
- Linux `6.8.0-142-generic`, x86-64, CPU `AMD EPYC Processor (with IBPB)`.
  Разрешённые CPU на хосте: 0–5; измерения закреплены за CPU 0 через affinity.
  Частота, turbo, фоновые процессы и гипервизор не контролировались.
- В итоговой серии N=16,20,24,26,28, семь повторов каждого алгоритма.
  Перед серией прогрев N=20; порядок всех запусков перемешан с seed=42.
  Каждый замер — новый процесс, генерация всей последовательности.
- `steady_clock` окружает только `generate` с одинаковой контрольной суммой
  для каждого алгоритма. Инициализация состояния внутри `generate` включена;
  запуск процесса, печать CSV, чтение `/proc`, Python и рендер исключены.
- Каждый ход потребляется по полям disk/from/to. Пустой `asm volatile`
  с read/write-регистровыми операндами не даёт GCC/Clang удалить вычисления
  или свести последовательность к заранее вычисленной сумме. После барьера
  выполняется одинаковый rotate/XOR-checksum, результат выводится после таймера.
  Это **генерация плюс общий минимальный потребитель**, не число «чистых» тактов
  инструкций алгоритма. Зависимости checksum и барьер ограничивают оптимизацию,
  поэтому потребитель с другой работой может изменить относительные результаты.
- Скрипт проверяет совпадение checksum всех алгоритмов для каждого N. Это
  защита измерений от ошибок, а не замена независимых тестов допустимости ходов.
- Пропускная способность = `(2^N−1) / median(seconds)`. Приведены медианы,
  диапазон min–max и максимальный пиковый RSS среди повторов. Доверительные
  интервалы и статистическая значимость не оценивались; выбросы не удалялись.
- RSS — `VmHWM` из `/proc/self/status`: максимум резидентной памяти текущего
  образа процесса, включая runtime/библиотеки/стек, после генерации. Первоначально
  опробованный `getrusage(RUSAGE_SELF).ru_maxrss` показывал около 13 MiB,
  унаследованных от Python при запуске. Его заменили до сохранённой baseline-серии.
  RSS порядка 3 MiB почти полностью определяется окружением; разницу 260 байт
  и O(N)-стека этот счётчик с гранулярностью страниц не способен надёжно выявить.
  O(1)/O(N) памяти устанавливается анализом кода, а не близостью RSS.

Базовый Docker-образ закреплён digest; apt-пакеты не закреплены snapshot-репозиторием.
Версии, affinity, CPU и SHA-256 измеренного бинарника записаны рядом с CSV.
Для повторения использовался build-образ
`sha256:c3d7f03649187351f2fe76712a504a1815e8181e52516f8302e77f26123e923b`,
в который примонтированы текущие исходники; release-сборка выполнена внутри него.

```sh
docker build --target build -t hanoi-build .
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" -w /work hanoi-build \
  sh -c 'cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j2 && python3 benchmarks/run.py --cpu 0 --repeats 7 --sizes 16 20 24 26 28 --output benchmarks/results.csv'
```

Выберите доступный CPU вместо 0 при необходимости. Не запускайте сборку,
санитайзеры или параллельные замеры одновременно с измерениями. Исходный
скрипт по умолчанию делает более короткую серию из пяти повторов до N=26.

На N=28 итерация генерирует 268 435 455 ходов за медианные 0.723406 с:
371.07 млн ходов/с против 232.90 млн у рекурсии и 251.44 млн у `formula`.
В данной серии это примерно 1.59× к рекурсии и 1.48× к `formula`.
Преимущество наблюдается и на N=24,26, что обосновывает выбор CLI по умолчанию.
Это не означает, что порядок сохранится на любом CPU, компиляторе или callback.

При N=24→26→28 число ходов увеличивается примерно в четыре раза на шаг;
медиана `iterative` меняется 0.046936→0.193743→0.723406 с (≈4.13×, ≈3.73×).
Это согласуется с Θ(2^N) и постоянной амортизированной работой на ход.
Малые N дают короткие интервалы; диапазоны времени показывают заметный шум
виртуальной среды. Не следует трактовать последние цифры как гарантированную
скорость или утверждать по этим данным отсутствие джиттера.

## Реализованные оптимизации

1. Потоковая выдача: последовательность не сохраняется, количество ходов не
   влияет на занимаемую память. Шаблонный callback допускает встраивание;
   нет `std::function`, виртуальных вызовов или аллокаций на каждый ход.
2. Выбор алгоритма и режима вне горячего цикла. `quiet` не конструирует
   визуализатор, не проверяет флаг визуализации на каждом шаге и не делает I/O
   до конца вычислений. Контрольная сумма — намеренная стоимость потребителя.
3. `iterative`: `std::countr_zero`, направление по чётности и одна коррекция
   значения 0…4 вместо деления; массив позиций выделяется один раз.
   После сравнений этот вариант выбран основным вместо первоначальной `formula`.
4. Два варианта O(1) управляющей памяти: `formula` с одним большим `%3` и
   `bitwise` с двумя. Они полезны при требовании отсутствия динамических
   выделений, но в текущих измерениях уступают хранению позиций.
5. Подсчёт отдельной формулой без запуска генератора. Это отдельная операция,
   не ускорение выдачи экспоненциальной последовательности.

## Проверенные и отклонённые варианты

- **Основной генератор `formula` без состояния.** Меньшая память и один остаток
  не превратились в лучшую скорость. Оставлен как доступный вариант, отклонён
  как алгоритм по умолчанию. Аналогично `bitwise` не выиграл сравнение.
- **Таблица `cycle[2][4]` вместо выбора направления и коррекций в `formula`.**
  Исходный код находится в начальном коммите `c091da1`;
  [патч эксперимента](../benchmarks/experiments/formula-table.patch) полностью
  описывает изменение, его можно применить к тому коммиту или текущему ядру
  в отдельной рабочей копии. Условия: тот же build-образ, флаги, CPU, пять
  повторов, N=16,20,24,26. Все тесты прошли перед измерениями.
  [Baseline CSV](../benchmarks/baseline.csv),
  [baseline таблица](../benchmarks/baseline-table.md),
  [baseline окружение](../benchmarks/baseline.environment.txt);
  [эксперимент CSV](../benchmarks/table.csv),
  [таблица](../benchmarks/table-table.md),
  [окружение](../benchmarks/table.environment.txt).
  На N=24 медиана formula изменилась 0.066681→0.096507 с, на N=26
  0.267300→0.267192 с. Из-за шума нельзя делать строгий вывод о замедлении;
  устойчивого выигрыша не получено, таблица удалена из окончательного ядра.
- **`getrusage` для памяти** проверен и заменён на `VmHWM` по причине наследуемого
  пика родительского процесса. Первые диагностические замеры с этим счётчиком
  не включены в сохранённые серии и не используются для итоговых выводов.

Ручное разворачивание цикла, SIMD, многопоточность, asm-генератор, огромные
таблицы и `-march=native` **не проверялись экспериментально**. Их нельзя называть
проигравшими вариантами. Для текущего объёма задачи выбран переносимый C++20;
дополнительные оптимизации требуют отдельного профилирования и измерений.

## Ограничения

- Полная генерация остаётся экспоненциальной. N=64 поддерживается арифметически,
  но полный перебор не проверялся и практически неосуществим; тестируются
  префиксы, последние ходы, степени двойки и случайные номера.
- Результаты относятся к нашим четырём реализациям. Исходники FXT изучены
  и сопоставлены в research.md, но их демонстрационные программы с печатью
  не выдаются за сопоставимый benchmark без вывода.
- Тесты охватывают C++20/GCC на x86-64 Linux. Другие архитектуры и компиляторы
  не измерены. Только измерительный барьер использует расширение GCC/Clang;
  алгоритмическое ядро — стандартный C++20.
- RSS содержит runtime процесса и не разделяет heap/stack по алгоритмам;
  в диапазоне N≤64 различия слишком малы для точного вывода по RSS.
- ASCII/ANSI и задержки намеренно не включены в сравнительное время генерации.
  Они проверяются функционально; скорость терминалов не сравнивалась.

## Выполненные проверки

- Release CTest в multi-stage Docker-сборке: **2/2 пройдены** (`core`, `cli`).
- Debug с AddressSanitizer и UndefinedBehaviorSanitizer: **2/2 пройдены**,
  ошибок санитайзеров не обнаружено. Команды приведены в README.
- Для N=0…12 полностью проверяются каждый ход, правила и конечное состояние
  всех четырёх алгоритмов, совпадение последовательностей и ограниченных префиксов.
  BFS по всем достижимым состояниям для N≤6 независимо проверяет длину минимума.
- Для N=1…64 проверяются префиксы, 1000 номеров на N (включая последний),
  степени двойки и соседние номера. Независимый оракул спускается по рекурсивному
  дереву, не использует формулу ctz/modulo. В частности проверен ход диска 64.
- CLI: границы 0/64/65, переполнение чисел, отрицательные/неполные аргументы,
  несовместимые параметры, безопасные лимиты, `--all`, четыре алгоритма,
  snapshot ASCII, управляющие ANSI-последовательности, задержка, ошибка `/dev/full`.
- Собран и запущен финальный runtime-образ `hanoi`:
  `sha256:70cc42c5d98c9bddae62b9a5256b7f155b84c1a4fa7879440ecee81932846cca`.
  Отдельно проверены count при N=64, все ходы N=3, quiet, ASCII, ANSI с задержкой,
  отклонение N=65 и пользователь `65534:65534`. Компилятор в runtime не нужен.
- Отклонённый патч проходит `git apply --check`, исходные CSV содержат все повторы.
